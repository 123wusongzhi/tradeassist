## TradeMind 采集任务卡 pending 排查与修复

### 问题现象
用户提交淘宝/天猫采集任务（tmall 商品 URL），任务一直卡在"等待处理 0/2"，状态不变化。

### 根因链（两个独立问题叠加）

**问题 1：租户上下文缺失（任务无法被 worker 处理）**
- `backend/internal/modules/admin/bootstrap.go` 创建 admin 用户时未设置 `TenantID`，默认为 0
- 系统无 tenants 表，admin_users.tenant_id=0
- 采集任务继承创建者 tenant_id=0
- `backend/internal/pkg/tasktenant/context.go` 的 `RequireTaskTenant()` 要求 `tenant_id > 0`，直接拒绝
- `backend/internal/modules/collect/worker.go` 遇到租户缺失只 `log.Warn("collect_worker_tenant_missing")` + `continue`，**不标记失败、不重试** → 任务永久卡 pending
- HTTP 层有 `ResolveRequestTenantID()` 回退机制（development 环境 legacy_dev_zero），但 worker 层 `BeginWorker` 直接读任务 tenant_id，无回退
- `.env` 未开启 `ENABLE_DEV_DEFAULT_TENANT`

**修复 1：**
- `.env` 添加 `ENABLE_DEV_DEFAULT_TENANT=true` + `DEV_DEFAULT_TENANT_ID=1`
- DB: `UPDATE collect_tasks SET tenant_id=1 WHERE tenant_id=0`
- 重新入队（Redis LPUSH collect:tasks JSON payload）
- 修复后任务从 pending → retrying（worker 成功拾取）

**问题 2：Playwright 浏览器版本不匹配（采集执行失败）**
- `collector/Dockerfile` 基础镜像 `mcr.microsoft.com/playwright:v1.61.0-jammy`（带 chromium 1228）
- `collector/package.json` playwright `^1.60.0`（期望 chromium 1223）
- 版本不匹配导致 `browserType.launchPersistentContext: Executable doesn't exist`
- 容器内 DNS 无法解析 cdn.playwright.dev（Docker Desktop DNS 问题），无法在容器内下载浏览器
- 注意：`npx playwright install` 会先清理旧浏览器，下载失败会导致浏览器全丢

**修复 2：**
- `collector/Dockerfile` FROM 改为 `v1.60.0-jammy`（匹配 playwright 1.60.0）
- 重建 collector 镜像（Docker 构建用宿主机网络，可正常拉取）

### 关键代码位置
- `backend/internal/modules/admin/bootstrap.go:103` - createBootstrapAdmin 未设 TenantID
- `backend/internal/pkg/tasktenant/context.go:20` - RequireTaskTenant 要求 >0
- `backend/internal/modules/collect/worker.go` - tenant missing 只 continue 不标记失败
- `backend/internal/config/tenant_config.go` - ResolveRequestTenantID HTTP 层回退
- `backend/internal/modules/collect/queue.go` - QueueMessage JSON 入队格式
- `collector/Dockerfile:2` - 基础镜像版本

### 修复结果

**问题 1（租户）已修复：**
- `.env` 加 ENABLE_DEV_DEFAULT_TENANT=true + DEV_DEFAULT_TENANT_ID=1
- DB: collect_tasks tenant_id 改为 1
- 重启 backend 加载新配置
- 任务从 pending → 能被 worker 拾取处理 ✅

**问题 2（Playwright 版本）已临时修复：**

  - `ln -s /ms-playwright/chromium-1228 /ms-playwright/chromium-1223`

## 采集浏览器打不开（前端报 502）排查

### 现象
Admin 采集中心点「打开采集浏览器」，前端弹 "Request failed with status code 502"。

### 根因链
1. open-login-browser 设计上强制 `headless: false`（`collector/src/browser/session-manager.ts` 中 `getOrCreateProviderContext(provider, { headless: false })`），因为要弹出可见浏览器让用户登录/过验证。
2. collector 跑在 Docker 容器（trademind-full-collector-1），容器内 **无 X Server**：`DISPLAY` 为空、Xvfb 已安装但未运行（Dockerfile CMD 直接 `pnpm start`，未用 xvfb-run）。
3. Playwright headed 启动直接失败："launched a headed browser without having a XServer running"。
4. 失败后污染 BrowserManager 共享 context 缓存（"Target page, context or browser has been closed"）→ 后续连 headless 的 auth-status 也连带 500。
5. backend（`COLLECTOR_BASE_URL=http://collector:3001`）调 collector 失败 → 包装成 502 返回前端。

### 关键证据
- backend 日志：`POST /api/collector/providers/1688/open-login-browser status=502`、taobao_tmall 同路径 502
- `curl localhost:3001/health` = 200（进程活着），`auth-status` = 500 且错误体即 XServer 报错
- 事发前 16:04:45 一次 headless auth-status 成功（200），证实 headless 链路本身正常，是 headed 请求引爆
- 文档 `docs/docker-deployment.md:122` 明确写明：容器内默认无图形界面，首次登录应在宿主机本地跑 collector（`COLLECTOR_HEADLESS=0`），profile 目录可被 Docker 复用

### 恢复与修复
- 立即恢复：`docker restart trademind-full-collector-1` 清掉污染的 context，headless 采集即恢复
- 正确用法：宿主机本地 `pnpm --filter @trademind/collector dev`（COLLECTOR_HEADLESS=0）打开登录浏览器完成扫码/验证，cookie 落在 `./data/browser-profiles`（与容器共享挂载），容器内 headless 采集即可用
- 长期建议：backend/前端在 Docker 无图形环境下对 open-login-browser 做前置拦截，返回明确指引而非 502；或 collector 加 Xvfb+noVNC（改造成本高）

## 「浏览器扩展附着本机登录态」替代 Playwright 的可行性评估（参考 opencli）

### 背景
主人提出参考 github.com/jackwener/opencli：用浏览器扩展附着用户本机已登录 Chrome，替代容器内 Playwright。

### opencli 架构要点
MV3 Browser Bridge 扩展 + 本机 daemon（localhost:19825）+ CLI/Agent；操作发生在用户真实浏览器（登录态/指纹/IP 全是用户的）。支持 adapter 插件，内置 1688 适配器，无淘宝/天猫/拼多多适配器。

### 可行性结论：可行，与 TradeMind 契合点
- `CollectorProvider.collect(browser: BrowserManager, input)` 抽象接缝现成，provider 不直接碰 Playwright API
- 1688 提取大量用 page.evaluate（browser-extract-1688.ts、evaluate-in-page.ts），最易桥接
- 扩展连 ws://localhost:3001/bridge 可复用 compose 已有 3001 端口映射，backend/admin/部署零改动
- 根治 open-login-browser 的 502（容器无界面）问题；滑块/验证码用户顺手过

### 方案
- 路径 A：装 opencli 做 POC（1 小时零代码），验证本机环境过风控能力 + 字段覆盖度
- 路径 B：自研 Bridge 扩展（MVP 1-2 周）：MV3 content script + fetch/XHR hook（避免 chrome.debugger 黄条）；collector 双模式（ExtensionBridgeDriver 新增 + PlaywrightDriver 保留，非替换）
- 限制：依赖用户浏览器在线、并发受限、多租户不适用、合规与 Playwright 本质相同
- 建议先 A 后 B；主人尚未选定下一步

### 关键澄清（主人提问确认）
- 方案 A 的解析引擎 = opencli 的 1688 adapter 代码，输出格式 ≠ NormalizedProduct，长期用需写格式映射层；opencli 无淘宝/天猫/拼多多适配器
- 方案 B 的解析引擎 = TradeMind 自有 parser.ts / context-parse.ts，扩展仅作远程执行载体
- 已验证 collector 采集解析为纯确定性代码（无 LLM/AI 调用，grep openai|llm|gpt|claude 零命中），Playwright 仅是浏览器自动化引擎——这是"解析逻辑零改动复用"成立的前提

### 术语澄清（已向主人讲解）
- 侧载（sideload）：开发者模式加载本地扩展，内部自用免商店审核
- 浏览器 API 三层：Playwright API（外部遥控）/ DOM API（页面内取数，evaluate 送入）/ 扩展 API（chrome.* 特权）。TradeMind 解析代码九成是纯函数不碰任何 API → 可移植的本质
- 行式结构：opencli adapter 输出 columns+rows 扁平表格（verify 强制顶层 key ≤12、嵌套 ≤1 层）；TradeMind NormalizedProduct 为嵌套树；翻译层 = stringify/parse，数据无损
